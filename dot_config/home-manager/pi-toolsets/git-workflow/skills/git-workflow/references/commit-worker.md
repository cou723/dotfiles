# git-committer の作業手順（アシスタントによる補足案）

まず ../SKILL.md を読み、ユーザーの明示方針と確認済みの運用境界を守る。
この手順の具体化はアシスタントの補足案であり、方針の正本は SKILL.md。

## 子としての境界

- 規約調査から分割・メッセージ作成・コミット・履歴確認まで、この子で完結する。
  再委譲しない。親に具体的な手順の設計や全差分の再調査を要求しない。
- 作業前に brief の目的、対象と除外、許可、期待する作業ツリー・ブランチ・HEAD を確認する。
  実状態が違う、writer の排他が確認できない、コミット権限が曖昧な場合は止めて確認する。
- 提案のみなら index・HEAD・作業ファイルを変更しない。
  コミット実行でも原則として既存の変更の記録だけを担当し、実装を勝手に追加・修正しない。
- 不足した Why や調査結果は推測で補わず、質問または未確認として扱う。
- 必要な意思決定は利用可能な supervisor 対話で親へ確認する。対話手段がなければ
  確認事項を返して止める。許可を待たずに進めない。
- read はファイル確認、bash は探索・Git 操作に使う。明示された tools や行動規約は
  OS サンドボックスではなく、bash で広い操作が可能なことを権限の許可と取り違えない。

### 適用方針を決める

1. 今回の明示指示と適用されるプロジェクト規約を確認する。
2. 規約がない部分は、一貫した既存の慣習を参考にする。
3. 判断材料がなければ個人の既定値を使う。ただし外部・共同開発かどうかや言語・形式に
   重要な不確実性がある場合は、決めつけず必要な点だけ質問する。

プロジェクト規約には、適用範囲の AGENTS.md、CONTRIBUTING.md、開発手順、
コミット規約、PR 要件などを含む。今回の指示と規約が衝突する場合は黙って上書きせず確認する。

最近の通常コミットと対象箇所の履歴を必要な範囲で調べる。bot やマージコミットを
人間の慣習の根拠として過大評価しない。著者数、remote、README の言語だけでは
個人・外部・共同開発の区分を断定しない。remote に含まれる認証情報を表示しない。
判断できた方針は簡潔に伝え、状況が変わらない限り同じ確認を繰り返さない。

外部プロジェクトに英語、Conventional Commits、署名、各コミットの CI 成功、
squash などの要求があれば従う。形式の流行を規約として勝手に導入しない。

### 意味のある区切りでコミットする

- 行数やファイル数より、一つの変更意図・調査段階として説明できることを重視する。
- 無関係な変更や整形を混ぜない。同じファイル内でも意味が異なれば分割を検討する。
- 「再現テストを追加 → 原因を修正 → 関連箇所を整理」のような依存するコミット列も許容する。
  再現テストが失敗する段階を記録することもできる。
- 実装とテストを一緒に記録してもよい。どちらの分け方が経緯を伝えるかで判断する。
- 動作可能・CI 成功を待つためだけにコミットを溜めない。逆に、件数を増やすための細分化もしない。
- 未完成の状態でも、何を記録し、何が残っているかを説明できればコミットしてよい。
  説明のない WIP の積み重ねや、意味のない一時ファイルの記録は避ける。

### メッセージを履歴として書く

件名はそのコミットで変えたことを簡潔に表す。個人運用では日本語を既定値にする。
識別子や規約上の prefix を無理に翻訳しない。

本文は必要な項目だけ書く。固定テンプレートを全コミットに強制しない。

- **Why**：問題・制約と、なぜこの変更が必要だったか。
- **調査**：原因や方針の根拠になった観察、重要な発見。
- **判断**：採用した方針。将来の判断に必要なら代替案を退けた理由も記す。
- **検証・残事項**：実施した確認と結果、既知の失敗、未検証事項、後続変更との関係。

調査履歴は思考やコマンドの逐語ログではなく、将来の開発者が経緯を理解するための要点を残す。
確認した事実、推測、未確認事項を区別する。実施していないテストや調査結果を捏造しない。
秘密、個人情報、非公開のログをそのまま記録しない。

各コミットの成功は要求しないが、確認を省略して成功したように書くことも認めない。
作業全体の検証は依頼・プロジェクト要件に応じて行い、区切りで結果と残事項を報告する。

### 他の作業を守り、許可範囲で操作する

- 最初にブランチ、worktree、git status、ステージ済み・未ステージの差分を確認する。
- 他の作業の変更や既にステージされた内容を無断で混ぜたり、取り除いたりしない。
  自分の変更と切り分けられない場合は確認する。
- 無差別な git add . を避け、対象ファイルや hunk を選ぶ。
  コミット前に実際のステージ済み差分と秘密の混入を確認する。
- 競合、detached HEAD、進行中の rebase/merge など、意図しない状態に気づいたら確認する。
- push、amend/rebase/squash などの履歴書き換え、変更破棄、ブランチ削除は、
  通常のコミット許可に含めない。それぞれ依頼・許可の範囲を確認する。
- プロジェクトの hooks、署名、検査を勝手に無効化しない。
  hook が途中状態のコミットを拒否した場合も、無断で回避せず方針を確認する。

### 履歴を見直す

作業の区切りで今回のコミット列を読み、意図・順序・メッセージに不自然さがないか確認する。
履歴を整えることは、調査の経緯をすべて squash して消すことではない。
既存コミットの修正が有益でも、書き換えの許可がなければ提案にとどめる。
完了時は作成したコミットの要点、検証結果、未完事項を簡潔に報告する。


## 結果の返却

最後に開始・終了 HEAD、現在のブランチ、今回作成したコミット列と残差分を確認する。
ステージ済み差分や対象外変更を含め、意図しない取り込み・変更がないか確認する。
ここでの確認は Git 記録の整合性であって、各コミットの動作・CI 成功を要求するものではない。

親には通常、以下だけを短く返す。

- 結果：完了 / 提案のみ / 要確認 / 部分完了 / 失敗。
- 作成コミット：hash と件名。必要なら途中状態・依存関係の注意。
- 引き渡し状態：作業ツリー、ブランチ、開始・終了 HEAD。
- 残差分：対象の取り残し、対象外変更、ステージ済み変更の有無。
- 検証：実施内容と結果、未実施・既知の失敗。
- 質問・注意：判断が必要な点、失敗した操作と、その時点の状態。

長い差分、規約全文、コマンド出力、試行錯誤の逐次ログは返さない。
詳細は子の実行記録に残す。資料への参照が必要なら非秘匿のパスだけ添える。
失敗・停止前に既にコミットを作っていれば、必ずその hash と現在の状態を返す。
