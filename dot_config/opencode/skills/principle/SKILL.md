# 原則に基づく運用

このスキルは、タスク固有の手順ではなく、意思決定の基準としてプロジェクトの原則を維持するために使用します。

## 適用範囲

- 原則を変更する前に、`docs/principles/` 配下のすべての Markdown ファイルを確認してください。
- 原則を、全体に適用される強制用プラグイン（global enforcement plugin）から独立させてください。
- プロジェクト固有のルールは、このグローバルなスキル内ではなく、プロジェクト内に記述してください。
- 洗練された成果物（アーティファクト）を、実質的な品質の証拠として扱わないでください。

## 作成ルール

1. 具体的な行動を規定する前に、意図する価値や成果を明記してください。
2. 各原則を、単独でレビューできるようにしてください。
3. 適用範囲と、観測可能な証拠を定義してください。
4. 例外は明示的かつ限定的に記述してください。
5. 一般的なルールよりも、より具体的なルールを優先してください。
6. 優先順位を無理に設定するのではなく、競合や未解決のトレードオフを記録してください。
7. 他の場所で既に管理されている手順の重複を避けてください。

各原則には、以下の項目のうち必要なものだけを含めてください。

- **Intent（意図）**: その原則によって守られる実質的な価値。
- **Rule（ルール）**: デフォルトの意思決定基準。
- **Applies when（適用条件）**: 関連するコンテキスト。
- **Exceptions（例外）**: デフォルトのルールを上書きする条件。
- **Evidence（証拠）**: 評価を可能にする、低コストで確認できる事実。
- **Priority（優先順位）**: 競合する原則との関係。

## レビュー

原則を以下の観点で評価してください。

- 実質的な価値と、単なる「完了したように見える状態」とを区別しているか。
- 低コストの評価者が、利用可能なコンテキストから準拠状況を判断できるか。
- 証拠の要件がリスクに見合っているか。
- 例外の範囲が限定されており、優先順位が明確か。
- 無​​駄なチェックを助長することなく、人の介入を減らすルールになっているか。

曖昧さを解消する最小限の変更を優先してください。単に文体の一貫性を保つためだけに、安定している原則を書き直さないでください。
