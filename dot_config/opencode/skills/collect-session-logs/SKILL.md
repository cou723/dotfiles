# collect-session-logs

過去の Claude Code 実行を調査するために、**1 つのセッションに関係するログファイル群**をまとめて特定・相関付けし、失敗箇所まで提示するスキルです。

## 反応する状況

- 過去の Claude Code セッション・実行の調査（「前回のセッションを調べて」等）
- 失敗した実行のログ収集・失敗箇所の特定
- サブエージェント・レビュー・バックグラウンドセッションのログの特定
- プラグイン/フックの挙動デバッグ

## Claude Code のログ配置（前提知識）

メインの transcript だけ見ても全体は分からない。サブエージェント・レビュー・バックグラウンドタスクは**別ファイルの独立セッション**として保存され、親への明示リンクが無いため、マーカー＋時刻窓＋内容で紐づける必要がある。

- **transcript ディレクトリ**: `~/.claude/projects/<ENCODED>/`
  - `<ENCODED>` = プロジェクト絶対パスの `/` と `.` を `-` に置換したもの（先頭も `-`）。
    例: `/home/u/ghq/github.com/x/repo` → `-home-u-ghq-github-com-x-repo`
  - 各セッション = `<sessionId>.jsonl`（1 行 1 JSON レコード）
  - `sessions-index.json` に `entries[{sessionId, fullPath, fileMtime}]` があり列挙・時刻ソートに便利
- **MCP ログ**: `~/.cache/claude-cli-nodejs/<ENCODED>/mcp-logs-<server>/<ISO>.jsonl`
- **セッションの種別判定**:
  | 種別 | 見分け方 |
  |------|---------|
  | 対話（メイン/人間起動） | `cwd`・`gitBranch` が入っている。最初の user の `promptSource` が `sdk` 以外。スラッシュコマンドを含むことが多い |
  | SDK 起動（サブエージェント/レビュー/バックグラウンド） | 先頭行が `type:queue-operation, operation:enqueue`。最初の user が `promptSource:"sdk"`。`cwd`・`gitBranch` が null |
  | 同一プロセス内サブエージェント（Task ツール） | 親ファイル**内**に `isSidechain:true` レコードとして埋め込まれる（別ファイルではない） |
- **重要な制約**: SDK 起動セッションには**親セッションへの明示的なリンクが無い**。`parentUuid` はファイル内のレコード連鎖を繋ぐだけ。よって相関はヒューリスティック（下記）。

## 対象

ユーザーの依頼で指定されていなければ、cwd のプロジェクトの「直近の対話セッション」をアンカーにする。
- パス（リポジトリ）… そのプロジェクトを対象にする
- セッション ID … そのセッションをアンカーにする
- `latest` … cwd プロジェクトの最新対話セッション（デフォルト）

## 手順

### 1. 対象ディレクトリを解決
cwd（または依頼のパス）から `<ENCODED>` を導出し、transcript ディレクトリと MCP ログディレクトリを確定する。両方の存在を確認する。

### 2. アンカーセッションを特定
- 依頼がセッション ID を指定していればそれ。
- それ以外は、対話セッションのうち最新（または調査対象として妥当なもの）を選ぶ。最初の user メッセージ（スラッシュコマンドや依頼内容）と開始/終了 timestamp を控える。
- アンカーの**活動時間窓** `[start, end]` を求める（最初と最後のレコードの timestamp。前後に数分のバッファを取る）。
- そのリポジトリで作業した痕跡（プラグインの状態ファイル等があれば、その mtime も窓の根拠に使う）。

### 3. 関係する SDK 起動セッションを収集
時間窓内に mtime/timestamp がある `.jsonl` のうち、**SDK 起動マーカー**（先頭 `queue-operation:enqueue` または `promptSource:"sdk"`）を持つものを候補にする。次で相関を強める:
- **内容の重複**: enqueue の `content`（変更ファイル一覧・diff・プロンプト）がアンカーの扱うリポジトリ/ファイルと一致するか。
- 同種の依頼テキスト（例: レビュー指示文）の一致。
誤検出を避けるため、時間窓に入っていても内容が無関係なものは除外し、判断根拠を残す。

### 4. 同一プロセス内サブエージェントも確認
アンカーファイル**内**の `isSidechain:true` レコードと `Task` ツール呼び出しを確認する（別ファイルではなくここに入る形式もあるため）。

### 5. MCP ログを付随収集
`mcp-logs-*` 配下で時間窓に入るファイルを拾う（外部呼び出しの失敗調査用）。

### 6. 失敗箇所を検出
各セッションについて次を判定:
- `isApiErrorMessage:true` / `apiErrorStatus` / トップレベル `error` を持つレコード
- 末尾テキストに `API Error` / `429` / レート制限などのエラー
- 異常に短い・要約や終了シグナル無しで途切れているセッション

## 出力

1. **相関マップ**（時刻順テーブル）: 時刻 / ファイルパス / 種別（対話・SDK派生・MCP）/ トピック / 結末（✅完了 / ❌エラー内容）
2. **失敗ハイライト**: どのファイルの何が原因で止まったか
3. **解決済みフルパス一覧**: ユーザーがそのまま開けるように
4. 相関が確実でないものは「根拠と確度」を明示

絶対パスは `file_path:line` 形式が使えるなら使い、クリックで開けるようにする。

## 注意事項

- 相関はヒューリスティック（SDK 起動セッションは親への明示リンクが無いため）。時刻窓の一致だけでは断定せず、内容・依頼テキストの一致で根拠を示し、確度不明な場合はそう明記する
- 判定は根拠を明示しつつ、推測を混ぜない
