# OpenCode セッション評価

指定された OpenCode V2 セッションを**読み取り専用**で評価する。評価対象はユーザー要求の達成度、手戻り、ツール選択、既存の仕組みの干渉、親子間の伝達、コンテキスト効率。結論より先に観測事実を集める。改善案の適用やスキル・エージェント・プラグインの変更は、別途依頼がない限り行わない。

## 対象の決定

- セッション ID が与えられたらそれを使う。省略され、対象が一意に定まらないときは ID または対象プロジェクトを質問する。評価を行う**現在のセッション自身**を、依頼の対象として勝手に選ばない。
- `opencode api get /api/session/<ID>` で存在と位置を確かめる。別サーバーにある場合は、その接続先を確認する。DB の直接編集・サービスの再起動・セッションの export / import は不要。
- 子セッションは `parentID` で API から再帰的にたどる。fork は `fork.sessionID` と境界を確認し、親子とは区別する。対象範囲（親のみ / 子を含む）、途中実行か完了後か、対象を見られなかった部分を明記する。

## 定型集計

同梱の `scripts/session_metrics.py` を実行する。`opencode api` が使える環境で動作し、読み取り以外は行わない。

```sh
python3 ~/.pi/agent/skills/evaluate-opencode-session/scripts/session_metrics.py ses_xxx
python3 ~/.pi/agent/skills/evaluate-opencode-session/scripts/session_metrics.py ses_xxx --no-children
```

結果は JSON。`sessions[]` は個別セッションのメタデータ・実測トークン数・モデルごとの assistant ステップ・ツール別の呼び出し回数、エラー、所要時間、テキスト量。`total` は含めたセッションの合計（親子重複なし）。入力、出力、reasoning、cache.read / write は**別軸**で示し、cache を入力に足して「総トークン」と断定しない。セッションメタデータとステップ合計が合わなければ差を報告する。

**重要:** API はツールごとの正確な消費トークンを提供しない。ツール別 `input_chars` / `output_chars` は記録された文字数で、トークン推計でもコストでもない。画像・省略された出力・外部サービス内部・プラグイン内処理は計測外。親のツール呼び出しと子セッションのモデル消費は別々に数える。子セッションの返答を親が読んだ分は親の後続ステップの入力に含まれ得るため、ツール文字数とモデルのトークンを加算しない。モデル呼び出しの入力は履歴の再投入やキャッシュを含むため、ユニークな文章量とは異なる。

## 内容の評価

1. `opencode api get '/api/session/<ID>/message?limit=50&order=asc'` を使い、`cursor.next` をたどって**全ページ**の user / assistant / skill / system / compaction と tool content を確認する。次ページは `order` を外して `?limit=50&cursor=<cursor.next>` とする（cursor と order は併用できない）。必要なら子セッションも同様。トークン集計スクリプトは本文を出力しないため、実行結果だけで成否や因果を決めない。機密を含む生の transcript を共有・保存しない。
2. 最初の要求と途中の方向転換を分離し、期待成果物と実際の最終応答・ファイル変更・検証結果を照合する。途中実行や確認不能は未確認とする。
3. 同じ目的の調査、ツール連打、失敗→再試行、長大な出力、繰り返し読み込まれる手順を特定し、メッセージ ID / ツール名 / 時系列を証拠として残す。子に渡した指示と子の報告を親の次の行動と比較し、引き継ぎ不足・過剰な重複・不要な委譲・親への要約不足を確認する。
4. 使用された skill / agent / command / plugin / hook の定義と呼び出しの前後を照合する。`~/.config/opencode/`、対象プロジェクトの `.opencode/`、読み込まれた指示とプラグインの定義を必要な範囲で確認する。`opencode api get /api/plugin` や `opencode api get /api/config` で有効状態を調べられるが、**定義の存在と実際の発火は別**。フックの疑いが残る場合は、時刻・セッション ID で `~/.local/share/opencode/log/opencode.log` を照合し、ログに無いことだけをもって非発火と決めない。既存の `collect-session-logs` は Claude Code 専用、`evaluate-run` は issue-loop 専用なので混同しない。
5. ボトルネックはセッション別・モデル別の実測値とツール別の文字数/失敗数/時間を並べて判断する。`execute` 等のラッパーツール内で起きた外部呼び出しの内訳は、この集計だけでは分からない。大きいツール出力があっても、その全量がモデルへ渡されたと断定しない。改善候補には、出力の絞り込み、検索→必要部分だけ読む、不要なスキル読み込み抑制、親子間の短い成果物/根拠/未解決事項の受け渡し等を検討する。

## 改善案の選び方

- **スキル**: 今後もモデルが参照すべき判断基準・作業手順・例外を再利用する場合。`SKILL.md` に利用条件と判断を置き、機械的な反復は隣接する `scripts/` に分離する。
- **サブエージェント**: 独立した調査・検証・専門作業として切り出せて、毎回親のコンテキストに全手順を再投入する必要がない場合。入力契約（対象、制約、成功条件）と出力契約（結論、証拠、未解決事項）を定め、親から重要情報が抜けないかも評価する。
- **スクリプト/コマンド**: 判断を要しない決定的な抽出・集計・変換の場合。スキルを増やさずにスクリプト単体で済むこともある。
- **既存定義の修正/変更なし**: 重複するスキルやエージェントを作らず、根拠が弱ければ追加せず観測方法を提案する。フックの追加はイベント境界で自動実行が必要で、誤発火・遅延のコストが正当化できる場合に限る。

## 報告

日本語で、(1) 対象 ID・評価範囲と達成度、(2) 主要な観測事実と証拠（メッセージ ID・必要ならファイルパス）、(3) 親/子ごとのトークン表、モデル別実測とツール別**文字数**・回数・失敗数（区別を明記）、(4) 影響度順の改善案（何を、なぜ、スキル/サブエージェント/スクリプト/既存修正のどれで、想定される副作用、検証方法）、(5) 観測できなかった点を示す。数値と因果を混同せず、費用対効果が不明なら推測で節約量を提示しない。
